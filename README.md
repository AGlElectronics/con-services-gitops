# Con Services GitOps template

> [!WARNING]
> ## **NOT READY FOR PRODUCTION**
>
> Con Services is under active development. Expect breaking changes, missing
> features and bugs. Do not use it for real events or real data yet.

A blank production template for running Con Services on Kubernetes with
[Argo CD](https://argo-cd.readthedocs.io/). You make your own private copy,
fill in **one settings file, `cluster.yaml`**, and Argo CD installs and
keeps running everything else: certificates, the database, sign-in, Den
and the modules.

Cluster-wide services are **prerequisites** that the cluster operator runs
and the template only uses: Argo CD, cert-manager with trust-manager,
External Secrets Operator, OpenBao, the CloudNativePG operator with its
Barman Cloud plugin, LoadBalancer IPs and cluster DNS. Installing them is
not covered here; the
[prerequisites](https://aglelectronics.github.io/con-services/deploy/prerequisites/)
say what the template needs from each.

Full guide: <https://aglelectronics.github.io/con-services/deploy/>

## Quick start

You need a Kubernetes cluster that meets the
[prerequisites](https://aglelectronics.github.io/con-services/deploy/prerequisites/)
(3+ nodes, Cilium with the Gateway API, a default StorageClass,
cert-manager, trust-manager, External Secrets Operator, an initialised and
unsealed OpenBao, CloudNativePG), an S3 service, a domain, and `kubectl`,
`helm`, `git` and `jq` on your computer.

1. **Copy the template.** On GitHub, **Use this template → Create a new
   repository**, make it **private**, and clone it.
2. **Fill in `cluster.yaml`.** Replace every `change-me`; until the file is
   complete, rendering stops and lists what is missing:

    ```sh
    grep -n change-me cluster.yaml          # prints nothing when done
    helm template root charts/root -f cluster.yaml > /dev/null && echo OK
    ```

    Then pick the modules to run: under `modules:` set `enabled: true`
    for each one you want (all are off by default; Den is always
    installed). Each module shows up unpaired on Den's **Modules** page
    and waits for Den until you pair it there
    ([Deploy the apps](https://aglelectronics.github.io/con-services/deploy/apps/)).

3. **Check Argo CD.** It must already run in the cluster and have the
   health check for Application objects in `argocd-cm` (the block under
   `configs.cm` in `bootstrap/argocd/values.yaml`); without it every sync
   wave starts at once:

    ```sh
    kubectl -n argocd get cm argocd-cm -o yaml | grep -c health.argoproj.io_Application   # prints 1
    ```

4. **Let OpenBao trust the template (OpenBao administrator, once).** This
   writes two policies and a narrow role for the template's setup Job; the
   admin token is asked for and never stored in the cluster:

    ```sh
    bash bootstrap/scripts/openbao-configure.sh
    ```

5. **Commit, push, and create the root Application.** The script first
   checks that the prerequisites are installed:

    ```sh
    git add cluster.yaml && git commit -m "Configure cluster" && git push
    bash bootstrap/install-root.sh
    ```

6. **Review and sync `openbao-setup`.** Argo CD stops at this Application
   (manual sync) until you have looked at its diff and pressed **Sync**. Its
   Job enables the KV engine in OpenBao and writes External Secrets' role;
   External Secrets then creates every random secret (database passwords,
   tokens) by itself. Set `openbao.setup.enabled: false` in `cluster.yaml`
   if the template must not touch OpenBao's configuration.

7. **Do the steps only a person can do:** enter your provider credentials
   in OpenBao (S3 keys, SMTP, DNS token; `openbao-seed.sh` asks for them),
   and create the DNS records and the S3 buckets. Argo CD waits for them
   and continues by itself.

Each step is explained, with expected output and troubleshooting, in the
[installation guide](https://aglelectronics.github.io/con-services/deploy/argocd/).

## What you get

| Layer | Components | High availability (default) |
| --- | --- | --- |
| Certificates | Let's Encrypt ClusterIssuers and the Con Services internal CA, on the cluster's cert-manager and trust-manager | |
| Secrets | OpenBao setup Job (reviewed before it runs), ClusterSecretStore `openbao` for the cluster's OpenBao and External Secrets Operator, random secrets generated by External Secrets | |
| Network | Gateway API (public and internal Gateway), Cilium network policies | default-deny in every Con Services namespace |
| Data | PostgreSQL cluster on the cluster's CloudNativePG with backups to S3 (Barman Cloud plugin); files at a **managed S3 service** | 3 PostgreSQL instances, quorum synchronous replication |
| Identity | Keycloak via the Keycloak Operator | 2 instances, shared sessions |
| Apps | Den and the modules, from the Helm charts of `AGlElectronics/con-services` | web apps 2+ replicas with PDBs |

Every container has CPU and memory requests and limits. Defaults total
about 2.1 CPU and 6.4 GiB of requests with five modules, not counting the
prerequisites; see
[Sizing](https://aglelectronics.github.io/con-services/deploy/sizing/).

## Layout

```text
cluster.yaml                  The only file you edit
charts/
  root/                       Renders every Argo CD Application from cluster.yaml
    values.yaml               Defaults of every setting (override in cluster.yaml)
    values.schema.json        Rejects unknown or misspelt keys
  module-extras/              ExternalSecrets and access configs of Den and the modules
  postgres/, keycloak/, gateway/, secret-store/, openbao-setup/, ...
                              Small charts for the objects specific to an installation
components/                   Fixed Kustomize folders (internal CA, namespaces, ...)
bootstrap/                    Used by hand: install-root.sh, Argo CD values,
                              OpenBao configure and seed scripts
examples/                     cluster.example-filled.yaml, a complete example
ci/                           Render and validation scripts used by CI
```

The root chart renders one Application per component, ordered by sync
waves. Den and the module charts are read from
[`AGlElectronics/con-services`](https://github.com/AGlElectronics/con-services)
at the tag `charts.targetRevision`; their values are computed from
`cluster.yaml`.

## Conventions

- **One settings file.** Everything specific to an installation is in
  `cluster.yaml`. If you need to change a file elsewhere, that is a gap in
  the template: please open an issue.
- **Every version is pinned:** Helm chart versions, image tags
  (`MAJOR.MINOR.PATCH-BUILD` for Con Services images, never `latest`), and
  the tag of the main repository. The one exception is your copy itself:
  Argo CD follows its branch (`git.targetRevision`, default `main`),
  because a push *is* the deployment.
- **No secret in Git.** Secrets live in OpenBao; External Secrets Operator
  creates the Kubernetes Secrets (`ExternalSecret` objects are in Git,
  their values are not).
- **Data is never deleted by Argo CD.** The Applications holding the
  namespaces and the database have no deletion finalizer, and databases
  use `databaseReclaimPolicy: retain`.
- **Validate before you push:**

    ```sh
    helm template root charts/root -f cluster.yaml > /dev/null && echo OK
    ```

    CI (`.github/workflows/validate.yml`) additionally renders every
    Application, checks resources and image tags, and validates the output
    against the Kubernetes schemas.
