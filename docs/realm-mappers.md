# Audience mappers and group paths

An **audience** is a name in the `aud` claim of a token. Each Con Services
API accepts an access token only when `aud` contains its own name (`hr-api`
for HR, and the names in the table below). An **audience mapper** is the
Keycloak setting on a web app's client that adds that name.

A **group path** is how Keycloak writes a group into the `groups` claim.
With full paths on, the top-level group `den-admin` arrives as `/den-admin`.
The modules strip one leading `/` and ignore case, so `/den-admin` and
`den-admin` are the same grant. The rule is the one in the main repository,
[How groups are matched](https://aglelectronics.github.io/con-services/concepts/authentication/#how-groups-are-matched).

The names match the development realms
(`infra/keycloak/realm-conservices.json` and `realm-attendees.json` in the
main repository) and
[Audiences per API](https://aglelectronics.github.io/con-services/concepts/authentication/#audiences-per-api).

## What a new installation already has

The realm imports in `charts/keycloak/templates/` are generated by
`bootstrap/scripts/keycloak-realm.py`. They already contain every mapper
below. You do not add them by hand on a cluster whose realms have never
been imported.

The import lists every web app client, including a module that is still
off in `cluster.yaml`. Keycloak imports a realm only once, so turning a
module on later does not import the realm again; the client and its mapper
are already there. `--format json` writes the same mappers into plain
realm files for the Docker production path (`kc.sh start --import-realm`).

## Clients and audiences

| App | Realm | Client | Audience on the access token |
| --- | --- | --- | --- |
| Den | `conservices` | `den-spa` | `den-api` |
| HR | `conservices` | `hr-spa` | `hr-api` |
| Stash | `conservices` | `stash-spa` | `stash-api` |
| Rally, staff app | `conservices` | `events-spa` | `events-api` |
| Learn | `conservices` | `learn-spa` | `learn-api` |
| Finance | `conservices` | `finance-spa` | `finance-api` |
| Desk | `conservices` | `desk-spa` | `desk-api` |
| Tasks | `conservices` | `tasks-spa` | `tasks-api` |
| Wiki | `conservices` | `wiki-spa` | `wiki-api` |
| Rally, submission site | `attendees` | `rally-submit` | `events-public-api` |

The mapper's name is `audience` plus the audience (`audience hr-api`). It
uses **Included Custom Audience**. These API names are not Keycloak
clients, so **Included Client Audience** stays empty. **Add to access
token** is on. **Add to ID token** is off, so an ID token's audience stays
the client id (`hr-spa`). **Add to token introspection** stays on, which
is the Audience mapper's default.

Each staff client also has a mapper named `groups`
(`oidc-group-membership-mapper`) with **Full group path** on. `rally-submit`
has no groups mapper.

Confidential clients (`den-keycloak`, `hr-provisioner`, `learn-provisioner`)
have no audience mapper. Nothing in the browser signs in as those clients.

## Upgrade a realm that already exists

Do this before you upgrade Den, or any module, to a release that checks its
audience. The app's changelog says when that starts. Add the mapper for
Den and for each module you are about to upgrade. Add `rally-submit` in
the `attendees` realm before the submission site checks
`events-public-api`. A module you are leaving disabled can wait until you
enable it: an old realm will not gain the mapper on its own.

A push to this template does not change a realm Keycloak has already
imported.

Use the admin console (`https://<keycloak.adminHost>.<domain>`, default
`https://auth-admin.example.org`). The placeholders below are the client
and the audience from the table. The example uses `hr-spa` and `hr-api`.

### Admin console: audience mapper

1. Sign in to the admin console. In the top left, select the realm
   (`conservices`, or `attendees` for `rally-submit`).
2. Open **Clients** and click the client (`hr-spa`).
3. Open **Client scopes**.
4. Open the dedicated scope. Its name is the client id plus `-dedicated`
   (`hr-spa-dedicated`).
5. Choose **Add mapper → By configuration → Audience**.
6. Set **Name** to `audience hr-api`.
7. Leave **Included Client Audience** empty. Set **Included Custom
   Audience** to `hr-api`.
8. Set **Add to access token** to on.
9. Set **Add to ID token** to off. The form opens with this on; turn it
   off. An ID token must not carry the API audience.
10. Leave **Add to token introspection** on.
11. Save.

Repeat from step 2 for every client you are upgrading, with that row's
audience. Then sign out of the web app and sign in again. Access tokens
last 5 minutes, and a token issued before the mapper does not gain the
audience by itself.

### What the access token should contain

On the dedicated scope, open **Evaluate**, pick a user who can sign in to
that app, and open **Generated access token**.

- `aud` includes `hr-api` (Keycloak also puts `account` there).
- `groups`, for a person in `hr-admin`, includes `/hr-admin` after the
  group-path step below.

**Generated ID token** has `aud` equal to `hr-spa` only.

### Admin console: full group path

Still on each staff client's dedicated scope (not `rally-submit`):

1. Open the mapper named `groups`.
2. Set **Full group path** to on. Leave **Add to access token**, **Add to
   ID token** and **Add to userinfo** on, and leave **Token Claim Name**
   as `groups`.
3. Save.

Sign in again. A top-level group is then `/den-admin`, which matches a
grant stored as `den-admin`.

### `kcadm.sh`

Same change from the Keycloak admin CLI, if you would rather not click
through each client. `kcadm.sh` ships in the Keycloak image at
`/opt/keycloak/bin/kcadm.sh`.

The commands ask for the admin password at a prompt. Type it there. Do not
pass `--password`, and do not put the password in the shell history.

1. Open a shell in one Keycloak pod:

    ```sh
    kubectl exec -n conservices-identity -it keycloak-0 -- bash
    ```

2. Sign in to the admin API. Replace the host with
   `https://<keycloak.adminHost>.<domain>` and `admin` with your admin
   user in the `master` realm:

    ```sh
    /opt/keycloak/bin/kcadm.sh config credentials \
      --server https://auth-admin.example.org \
      --realm master \
      --user admin
    ```

    The name must be the admin console host. The certificate is issued for
    that name. You should get a prompt `Password:` and then no error.

3. Stay in that shell. This helper creates one audience mapper. A client
   that already has a mapper of that name is left as it is; open it in the
   admin console and check the audience and the two token switches.

    ```sh
    add_audience() {
      realm=$1
      client=$2
      aud=$3
      id=$(/opt/keycloak/bin/kcadm.sh get clients -r "$realm" -q clientId="$client" --fields id --format csv --noquotes | tail -n 1)
      /opt/keycloak/bin/kcadm.sh create "clients/${id}/protocol-mappers/models" -r "$realm" \
        -s "name=audience ${aud}" \
        -s protocol=openid-connect \
        -s protocolMapper=oidc-audience-mapper \
        -s "config.\"included.custom.audience\"=${aud}" \
        -s 'config."id.token.claim"=false' \
        -s 'config."access.token.claim"=true' \
        -s 'config."introspection.token.claim"=true'
    }
    ```

    Run one call per client:

    ```sh
    add_audience conservices den-spa den-api
    add_audience conservices hr-spa hr-api
    add_audience conservices stash-spa stash-api
    add_audience conservices events-spa events-api
    add_audience conservices learn-spa learn-api
    add_audience conservices finance-spa finance-api
    add_audience conservices desk-spa desk-api
    add_audience conservices tasks-spa tasks-api
    add_audience conservices wiki-spa wiki-api
    add_audience attendees rally-submit events-public-api
    ```

    Each new mapper prints `Created new model with id '…'`.

    The same call written out for HR, without the helper:

    ```sh
    id=$(/opt/keycloak/bin/kcadm.sh get clients -r conservices -q clientId=hr-spa --fields id --format csv --noquotes | tail -n 1)
    /opt/keycloak/bin/kcadm.sh create "clients/${id}/protocol-mappers/models" -r conservices \
      -s name="audience hr-api" \
      -s protocol=openid-connect \
      -s protocolMapper=oidc-audience-mapper \
      -s 'config."included.custom.audience"=hr-api' \
      -s 'config."id.token.claim"=false' \
      -s 'config."access.token.claim"=true' \
      -s 'config."introspection.token.claim"=true'
    ```

4. Point each staff client's `groups` mapper at the full path. This writes
   the whole mapper, the same fields the realm import has, with
   `full.path` true. `kcadm.sh update` replaces the mapper, so every field
   is sent again. There is no `groups` mapper on `rally-submit`.

    ```sh
    full_path_groups() {
      realm=$1
      client=$2
      id=$(/opt/keycloak/bin/kcadm.sh get clients -r "$realm" -q clientId="$client" --fields id --format csv --noquotes | tail -n 1)
      mid=$(/opt/keycloak/bin/kcadm.sh get "clients/${id}/protocol-mappers/models" -r "$realm" \
        --fields id,name --format csv --noquotes \
        | while IFS=, read -r row_id row_name; do
            [ "$row_name" = groups ] && printf '%s\n' "$row_id"
          done)
      /opt/keycloak/bin/kcadm.sh update "clients/${id}/protocol-mappers/models/${mid}" -r "$realm" \
        -s name=groups \
        -s protocol=openid-connect \
        -s protocolMapper=oidc-group-membership-mapper \
        -s consentRequired=false \
        -s 'config."full.path"=true' \
        -s 'config."id.token.claim"=true' \
        -s 'config."access.token.claim"=true' \
        -s 'config."claim.name"=groups' \
        -s 'config."userinfo.token.claim"=true'
    }
    ```

    One call per staff client:

    ```sh
    full_path_groups conservices den-spa
    full_path_groups conservices hr-spa
    full_path_groups conservices stash-spa
    full_path_groups conservices events-spa
    full_path_groups conservices learn-spa
    full_path_groups conservices finance-spa
    full_path_groups conservices desk-spa
    full_path_groups conservices tasks-spa
    full_path_groups conservices wiki-spa
    ```

    A successful update prints nothing. Read the mapper back and check
    `"full.path" : "true"`:

    ```sh
    /opt/keycloak/bin/kcadm.sh get "clients/${id}/protocol-mappers/models/${mid}" -r conservices
    ```

5. Sign out of each web app and sign in again.

`kcadm.sh` stores the admin session in the home directory of whichever
machine ran `config credentials`. On the pod that file disappears when the
pod restarts. It is not written to Git or to OpenBao.

## Docker production realms

From a checkout of this template, with the main repository beside it and
PyYAML installed (`pip install pyyaml`):

```sh
python3 bootstrap/scripts/keycloak-realm.py \
  --source ../con-services/infra/keycloak \
  --format json --domain con.example.org --out ./realm
```

That writes `realm/realm-conservices.json` and `realm/realm-attendees.json`
with the same mappers and with your domain filled in. Copy them to the
folder Keycloak imports from (`/opt/keycloak/data/import` when you start
with `--import-realm`). A realm that Keycloak has already imported is not
updated; use the steps above on that realm.

## Troubleshooting

### The API answers 401 and the body says invalid token

The access token's audience does not include the API name. The body is:

```json
{"error":{"code":"unauthorized","message":"invalid token"}}
```

Work down this list.

1. The client has no audience mapper, or **Included Custom Audience** is
   not the name in the table (`OIDC_AUDIENCE` on the module; Rally's
   submission site uses `ATTENDEE_OIDC_AUDIENCE`, default
   `events-public-api`). Add or correct the mapper, then sign in again.
2. The browser is still sending a token from before the mapper. Sign out
   of the web app and sign in again. Waiting out the 5 minute access token
   does the same.
3. **Add to ID token** was left on and the web app is sending the ID
   token. That token's `aud` is the client id (`hr-spa`). The API wants
   `hr-api`. Turn **Add to ID token** off and confirm the call sends the
   access token.
4. The mapper was added on the wrong realm (`rally-submit` is in
   `attendees`; every other row is in `conservices`).

Check with **Evaluate → Generated access token**, as above. `aud` must
include the API name.

### Sign-in works, but the person has no role or the wrong role

Sign-in succeeded, so the audience check passed. The group grant is what
failed. Den then drops the person's role (only `/api/v1/me` and their
preferences keep working) and a module answers 403 for the pages that
group should have opened.

1. Read `groups` on the generated access token.
2. With **Full group path** on, a top-level group is `/den-admin`. The
   modules remove one leading `/` and compare without case, so
   `/den-admin` matches a grant of `den-admin`. A fresh import already
   sends full paths. Set **Full group path** on, then sign in again, so
   this realm matches that import.
3. A nested group arrives as `/parent/den-admin`. That does not match a
   grant of `den-admin`. The groups shipped with the realm are top-level
   (`/den-admin`, `/hr-admin`, and the rest). A parent you add yourself
   has to be stored as the path after the one leading slash
   (`parent/den-admin`), or set as `OIDC_GROUP_PREFIX`.
4. If `groups` is missing, **Add to access token** on the `groups` mapper
   is off. Turn it on. The claim name stays `groups`.
5. An old token still has the previous `groups` value. Sign in again.

### `kcadm.sh` says the mapper already exists

That client already has a mapper of this name. Open it under the dedicated
scope and check **Included Custom Audience**, **Add to access token** and
**Add to ID token**. Do not create a second one. A client must carry
exactly one audience mapper, for its own API.

### `kcadm.sh` cannot verify the certificate, or the host does not resolve

Use the admin console host (`https://auth-admin.example.org`), not
`https://localhost:8443`. Inside the pod that name has to resolve to
Keycloak and the certificate has to match it. When it does not, run
`kcadm.sh` from a computer that can open the admin console, with a
Keycloak 26 `kcadm.sh`, and the same `config credentials` command.

### A newly enabled module 401s on a realm imported before this change

The realm was not imported again, so the new module's client may exist
without the audience mapper. Add that client's mapper (the table above)
before you start the upgraded module, then sign in again.
